⚙️ How the JVM Works
⚠️
This is a very common question. Be ready to explain the JVM flow and its key components clearly.
🔄 JVM Execution Flow
Core Concept

"The JVM (Java Virtual Machine) is the component that executes Java bytecode and allows the same program to run on any operating system without changes."

Compilation — .java code is compiled with javac to bytecode (.class). This bytecode is OS-independent.
Class Loading — The JVM loads necessary classes into memory using different classloaders (Bootstrap, Extension, Application).
Verification — The JVM validates bytecode to prevent unsafe or corrupted code.
Execution — Bytecode is executed in two ways: interpreted (line by line) or JIT compiled (Just-In-Time: compiles critical parts to native code for better performance).
Memory Areas
  • Heap: where objects live (managed by GC)
  • Stack: local variables and method calls (per thread)
  • Metaspace: class metadata
  • PC Register: execution tracking per thread
Garbage Collector

Automatically manages memory by removing unused objects. Algorithms: G1, ZGC, Shenandoah. Reduces memory leaks and simplifies development.

Execution Engine
  • Interpreter: fast startup
  • JIT Compiler: optimizes runtime performance by detecting and optimizing "hot code"
⚡ The Killer Feature of JVM
Must Know

"What is the killer feature of the JVM?"

"The killer feature of the JVM is its ability to combine portability with high performance through the Just-In-Time (JIT) compiler. It allows Java code to be written once, run anywhere, and still achieve near-native performance by optimizing hot code at runtime."

💡
Pro tip: "Unlike traditional compiled languages, the JVM can optimize based on real execution patterns, not assumptions made at compile time." — This shows deep understanding.
🌐 REST API Levels
ℹ️
The question "How many levels of REST do you know?" refers to the Richardson Maturity Model.
📊 Richardson Maturity Model
4 Levels

"REST has 4 levels according to Richardson's maturity model, from level 0 to level 3."

Level 0 – The Swamp of POX

Uses HTTP but without REST principles.

  • Single endpoint
  • Everything is POST
  • Example: /api for everything
Level 1 – Resources

Introduces resources.

  • Separate URLs per entity
  • Example: /users, /orders
  • But still misuses HTTP (everything POST)
Level 2 – HTTP Verbs

Correctly uses HTTP methods.

  • GET, POST, PUT, DELETE
  • Correct status codes (200, 404, 500)
  • ✅ This is REST "done right"
Level 3 – HATEOAS

API guides the client dynamically through links.

// Response includes navigation
{
  "user": "123",
  "links": [
    { "rel": "orders", "href": "/users/123/orders" }
  ]
}
💡
Industry reality: "In practice, almost nobody fully implements HATEOAS; level 2 is the industry standard."
🏗️ Microservices vs Monolith
🤔 Why Microservices? Why not Monolithic?
Architecture Decision

Brief Summary:

"Microservices solve organizational scalability, independent deployment, and resilience at the cost of greater operational complexity. A monolith is simpler and often sufficient; choose based on the real problem, not trends."

✅ Why Choose Microservices
  • Component scaling: scale only the service that needs more resources
  • Independent deployments: teams deploy without coordinating the entire system
  • Fault isolation: a failure in one service doesn't bring down the whole app
  • Heterogeneous technologies: each service can use the best-fit technology
  • Team ownership: self-contained teams with clear ownership
  • Incremental evolution: replace or version parts without rebuilding everything
⚠️ Microservices Costs
  • Operational complexity: needs orchestration, discovery, gateway, distributed logging, tracing
  • Higher latency: RPC/HTTP calls between services add latency
  • Consistency challenges: eventual consistency and distributed transactions (Sagas)
  • Complex testing: integration and E2E require simulated infra
  • Initial cost: infrastructure and DevOps skills increase time and budget
  • Observability required: without metrics/tracing, debugging is impossible
✅ Why Choose a Monolith
  • Simplicity to start: less infra, lower DevOps learning curve
  • Lower internal latency: in-memory calls, predictable performance
  • Simpler development and testing: single deployment, fewer mocks
  • Lower initial cost: ideal for MVPs or small teams
📋 When to Use Each
Decision Framework

Start with Monolith if:

  • You're a startup/MVP
  • Small team (<6-8 developers)
  • Product in exploration phase
  • Predictable load

Consider Microservices if:

  • Multiple teams (>8-10) blocking each other
  • Parts of the domain have very different scaling or availability requirements
  • Need independent deployments for business reasons
  • Have DevOps culture and capacity
💡
Middle ground: Modular Monolith — clear modules in a single codebase with well-defined boundaries; makes it easier to extract services later.
🎯 Domain-Driven Design (DDD)
📚 What is DDD?
Core Concept

"DDD (Domain-Driven Design) is a software design approach where development centers on the business domain. The idea is to model the system based on how the business actually works, using a common language between developers and domain experts."

Main Idea:

"The goal is for the code to directly reflect business rules, not just the technical part."

🗣️ Ubiquitous Language

A shared language between business and development to avoid misunderstandings. Terms used in code match exactly what the business uses.

🔲 Bounded Context

Divides the system into contexts where a model has a specific meaning. Different contexts can have different models for the same concept.

🏛️ Entities & Value Objects

Entities have identity (User with ID). Value Objects are immutable and defined by their values (Money, Address).

📦 Aggregates

Group entities and guarantee consistency through a root. Only the aggregate root can be referenced from outside.

💾 Repositories

Abstract data access. Provide collection-like interface for aggregates, hiding persistence details.

⚙️ Domain Services

Encapsulate business logic that doesn't naturally fit in entities or value objects.

💡
Why use DDD: "It helps manage complex systems, improves communication with business, and produces more maintainable code aligned with actual requirements."
⚠️
Common mistakes to avoid: Don't say "DDD is just using many layers" or "DDD is only architecture" — that shows you don't understand it well.
🔗 Linked Lists
⏱️ Access Complexity
O(n)

"What is the complexity to get an element from a linked list?"

"The complexity to get an element from a linked list is O(n), because you must traverse the list from the start until you find the element."

Why O(n):

  • In a linked list there's no direct access by index
  • Each node points to the next one
  • To reach position k, you traverse k elements
Array / ArrayList
// Direct index access
int value = array[5]; // O(1)

// Fast random access
ArrayList<Integer> list = new ArrayList<>();
int val = list.get(5); // O(1)
LinkedList
// Must traverse nodes
LinkedList<Integer> list = new LinkedList<>();
int val = list.get(5); // O(n)

// Sequential access required
💡
Pro tip: "Although insertion or deletion in a linked list can be O(1) if you already have the node reference, access is still O(n), making it less efficient for frequent reads."
🔄 Cycle Detection in Linked Lists
⚠️
This is a classic interview question. Be ready to explain Floyd's algorithm clearly.
🔍 The Problem
Classic Algorithm

Scenario: "A linked list where a node points to a previous node instead of the next one — for example, node 5 → node 3 instead of 5 → 6. This creates an infinite loop (cycle)."

Problem:

"In that case, there's no end to the list and traversing it can generate an infinite loop."

✅ Floyd's Algorithm (Tortoise and Hare)
Optimal Solution

"To detect this type of cycle, we use Floyd's algorithm with two pointers:"

Slow pointer — advances 1 step at a time
Fast pointer — advances 2 steps at a time
If there's a cycle — they will eventually meet
If no cycle — fast pointer reaches null
Java — Floyd's Cycle Detection
public boolean hasCycle(ListNode head) {
    if (head == null) return false;
    
    ListNode slow = head;
    ListNode fast = head;
    
    while (fast != null && fast.next != null) {
        slow = slow.next;        // Move 1 step
        fast = fast.next.next;   // Move 2 steps
        
        if (slow == fast) {
            return true;  // Cycle detected!
        }
    }
    
    return false;  // No cycle
}

Complexity:

  • Time: O(n)
  • Space: O(1) — only two pointers!
🔄 Alternative: HashSet Approach
Uses More Memory

"You can also use a HashSet to store visited nodes. If you see a node again, there's a cycle. But this uses O(n) space."

Java — HashSet Approach
public boolean hasCycle(ListNode head) {
    Set<ListNode> visited = new HashSet<>();
    ListNode current = head;
    
    while (current != null) {
        if (visited.contains(current)) {
            return true;  // Cycle found
        }
        visited.add(current);
        current = current.next;
    }
    
    return false;
}

Time: O(n), Space: O(n) — Floyd's algorithm is more space-efficient.

🧬 Why Do We Need Generics?
💡 Recommended Answer
Core Concept

"We need generics to write type-safe, reusable code that works with different data types without duplicating logic and without sacrificing compile-time type checking."

🔒 Type Safety

Without generics, collections stored Object, requiring manual casting that could fail at runtime with ClassCastException. Generics catch these errors at compile time instead.

♻️ Code Reusability

A single generic class like Box<T> works for Box<String>, Box<Integer>, etc. — no need to duplicate the class per type.

❌ Without Generics (Pre-Java 5)
List list = new ArrayList();
list.add("hello");
list.add(42); // no error at compile time

String s = (String) list.get(1);
// ClassCastException at RUNTIME
✅ With Generics
List<String> list = new ArrayList<>();
list.add("hello");
list.add(42); // ❌ COMPILE-TIME error

String s = list.get(0); // no cast needed
🛠️ Generic Methods & Bounded Types
Show Depth
Java — Generic method with bounded type
public static <T extends Comparable<T>> T max(List<T> list) {
    T result = list.get(0);
    for (T item : list) {
        if (item.compareTo(result) > 0) {
            result = item;
        }
    }
    return result;
}

// Works with any Comparable type: Integer, String, custom classes
Integer maxNum = max(List.of(3, 7, 1));
String maxStr = max(List.of("apple", "banana"));
💡
Senior answer: "Generics give us compile-time type safety, eliminate unnecessary casting, enable code reuse across types, and let the compiler catch type errors early instead of failing at runtime. They're also essential for building type-safe APIs like the Collections Framework and Streams."
🔒 Deadlocks
⚠️
This is a classic concurrency question. You need to explain what a deadlock looks like in practice AND name the 4 conditions (Coffman conditions) that must hold simultaneously.
🔄 What Does the Most Common Deadlock Look Like?
Classic Pattern

"The most common deadlock happens when two threads each hold a lock the other one needs — Thread A holds Lock 1 and waits for Lock 2, while Thread B holds Lock 2 and waits for Lock 1. Neither can proceed."

Java — Classic Two-Thread Deadlock
public class DeadlockExample {
    private static final Object lock1 = new Object();
    private static final Object lock2 = new Object();

    public static void main(String[] args) {
        Thread threadA = new Thread(() -> {
            synchronized (lock1) {
                sleep(100);
                synchronized (lock2) { // waits for lock2
                    System.out.println("Thread A acquired both");
                }
            }
        });

        Thread threadB = new Thread(() -> {
            synchronized (lock2) {
                sleep(100);
                synchronized (lock1) { // waits for lock1
                    System.out.println("Thread B acquired both");
                }
            }
        });

        threadA.start();
        threadB.start();
        // Result: both threads block forever waiting on each other
    }
}
📋 The 4 Coffman Conditions
Must Know All 4

"For a deadlock to occur, all four conditions must hold at the same time:"

Mutual Exclusion — At least one resource must be held in a non-shareable mode; only one thread can use it at a time (e.g. a synchronized lock).
Hold and Wait — A thread holding at least one resource is waiting to acquire additional resources currently held by other threads.
No Preemption — A resource can only be released voluntarily by the thread holding it; it cannot be forcibly taken away.
Circular Wait — A closed chain of threads exists where each thread waits for a resource held by the next thread in the chain (Thread A → waits for B → waits for A).
🛡️ How to Prevent Deadlocks
Follow-up Question

Breaking any one of the 4 conditions prevents deadlock:

  • Lock ordering: always acquire locks in the same global order (breaks circular wait)
  • Lock timeout: use tryLock(timeout) instead of blocking indefinitely (breaks hold and wait)
  • Avoid nested locks: minimize holding multiple locks simultaneously
  • Use higher-level concurrency utilities: java.util.concurrent (ConcurrentHashMap, ExecutorService) instead of manual locking
Java — Prevention with tryLock
if (lock1.tryLock(1, TimeUnit.SECONDS)) {
    try {
        if (lock2.tryLock(1, TimeUnit.SECONDS)) {
            try { /* critical section */ }
            finally { lock2.unlock(); }
        }
    } finally { lock1.unlock(); }
}
// If lock2 can't be acquired, thread backs off instead of blocking forever
💡
Senior answer: "A deadlock happens when two or more threads each hold a resource the other needs, and neither releases it. For this to occur, four conditions must hold simultaneously: mutual exclusion, hold and wait, no preemption, and circular wait. In practice, I prevent this by enforcing a consistent lock acquisition order across the codebase and using tryLock with timeouts instead of indefinite blocking."
🏛️ Clean Architecture
💡 What Is Clean Architecture?
Core Concept

"Clean Architecture is a way of organizing code so that business logic doesn't depend on frameworks, databases, or UI. Dependencies point inward — toward the domain — so the core of the application can be tested and changed independently of technical details."

🎯 The Dependency Rule
Key Principle

"Source code dependencies can only point inward. Nothing in an inner circle can know anything about something in an outer circle."

Layers (outer → inner)
Frameworks & Drivers  (Spring, DB, Web, UI)
        ↓ depends on
Interface Adapters    (Controllers, Presenters, Gateways)
        ↓ depends on
Application/Use Cases  (Business rules specific to the app)
        ↓ depends on
Entities                (Enterprise-wide business rules)

// Entities know NOTHING about Spring, JPA, or HTTP.
// Frameworks depend on the domain — never the other way around.
📦 Entities

Core business objects and rules, independent of any framework. E.g., an Order class with validation logic that doesn't know about databases or HTTP.

⚙️ Use Cases

Application-specific business rules — orchestrates entities to fulfill a specific operation, like "PlaceOrder" or "CancelSubscription".

🔌 Interface Adapters

Converts data between use cases and external formats — controllers, REST DTOs, repository implementations.

🖥️ Frameworks & Drivers

The outermost layer — Spring Boot, the database, web servers. Most volatile layer, easiest to swap out.

☕ Example in Java / Spring Boot
Practical
Domain layer — no framework dependencies
// Entity — pure Java, no annotations
public class Order {
    private final String id;
    private BigDecimal total;

    public void applyDiscount(BigDecimal percentage) {
        if (percentage.compareTo(BigDecimal.ZERO) < 0)
            throw new IllegalArgumentException("Invalid discount");
        this.total = total.subtract(total.multiply(percentage));
    }
}

// Use case — depends only on an interface (port), not the implementation
public class PlaceOrderUseCase {
    private final OrderRepository repository; // interface

    public PlaceOrderUseCase(OrderRepository repository) {
        this.repository = repository;
    }

    public void execute(Order order) {
        // business logic here
        repository.save(order);
    }
}
Infrastructure layer — implements the interface
@Repository
public class JpaOrderRepository implements OrderRepository {
    @Autowired private OrderJpaEntity jpaRepo;

    @Override
    public void save(Order order) {
        // maps domain Order to JPA entity and persists it
    }
}
✅ Benefits
  • Business logic testable without a database or web server
  • Swap frameworks/DB with minimal impact on core logic
  • Clear separation of concerns
  • Easier to onboard developers — logic isn't scattered across controllers
⚠️ Trade-offs
  • More boilerplate (interfaces, mappers between layers)
  • Overkill for small CRUD apps with little business logic
  • Requires team discipline to maintain the dependency rule
💡
Senior answer: "Clean Architecture enforces the Dependency Rule — inner layers (entities, use cases) never depend on outer layers (frameworks, DB, UI). This is achieved through interfaces: the domain defines a port like OrderRepository, and infrastructure provides the implementation. It's essentially Dependency Inversion applied at an architectural level, and it overlaps heavily with Hexagonal Architecture and DDD — the goal is always to protect business logic from technical churn."
⚠️
Common mistake: Don't say "it's just using layers" or "it's the same as MVC" — Clean Architecture is specifically about the direction of dependencies, not just having folders named controller/service/repository.
📨 Amazon SQS
☁️ What is SQS?
AWS Service

"SQS (Amazon Simple Queue Service) is a fully managed messaging service from AWS that allows you to decouple system components using queues. Producers send messages to the queue and consumers process them asynchronously."

📋 Standard Queue
  • High scalability
  • Best-effort ordering (not guaranteed)
  • At-least-once delivery (possible duplicates)
  • Nearly unlimited throughput
🎯 FIFO Queue
  • Guaranteed order
  • Exactly-once processing
  • No duplicates
  • Limited to 300 TPS (3000 with batching)
⚙️ Key Concepts
Must Know
ConceptDescription
Visibility TimeoutTime a message is hidden while being processed
Message RetentionHow long a message lives in the queue (default 4 days, max 14)
Dead Letter Queue (DLQ)Messages that fail multiple times are sent here for analysis
Long PollingReduces empty responses and costs by waiting for messages
👥 How Many Consumers Can SQS Have?
Scalability

Answer: "SQS has no fixed limit on consumers. You can have as many as you need."

Standard Queue:

"Allows multiple consumers without practical limit, with high concurrency, but may have duplicate messages and no guaranteed order."

FIFO Queue:

"Also allows multiple consumers, but processing is limited by message group IDs; within the same group, messages are processed sequentially one at a time. Different groups can be processed in parallel."

💡
Key point: "Parallelism in FIFO depends on how many message groups you have."
⚖️ SQS vs Kafka
🔄 Main Difference
Architecture Choice

"The main difference is that SQS is a managed queue service for simple decoupled messaging, while Kafka is an event streaming platform oriented towards event logs, with high retention and replay capability."

Amazon SQS
  • Model: Queue
  • Consumption: Messages consumed and deleted
  • Replay: No native replay
  • Management: Fully managed (no infrastructure)
  • Best for: Async tasks, decoupling microservices
Apache Kafka
  • Model: Distributed log (streaming)
  • Retention: Messages stored for defined time
  • Replay: Can re-read events
  • Management: Requires management (or MSK/Confluent)
  • Best for: Event streaming, analytics, data pipelines
📊 Key Differences
AspectSQSKafka
ConsumptionDeleted afterPersisted
OrderingFIFO onlyPer partition
ScalabilityAutomaticManual (partitions)
ComplexityLowHigh
🎯 When to Use Each

Use SQS if:

  • You want simplicity and quick decoupling
  • Task-based processing
  • Don't need replay

Use Kafka if:

  • Event streaming needed
  • Multiple independent consumers
  • Replay and audit capabilities
  • High throughput requirements
💡
Senior answer: "SQS is pull-based and oriented to task processing, while Kafka is log-based and allows multiple independent consumers with offsets, enabling replay and advanced parallel processing."
🔄 Event Streaming vs Event Sourcing
⚠️
Many developers confuse these two concepts. They're related but fundamentally different. Understand the distinction clearly.
🎯 The Core Difference
Critical Distinction

Recommended Answer:

"Event Streaming is the continuous flow of events through a system in real-time, while Event Sourcing is a design pattern where the application state is reconstructed from a sequence of stored events."

Event Streaming
Moving events → Transport & Processing
Event Sourcing
Storing events → Source of Truth
📡 Event Streaming

What it is:

"An architecture where events are produced, transmitted, and consumed in real-time."

Characteristics:

  • Events flow continuously through the system
  • Multiple consumers react to events in real-time
  • Events may or may not be stored permanently
  • Focus on transport and delivery

Examples:

  • Log aggregation (ELK stack)
  • Click stream analytics
  • Real-time notifications
  • IoT sensor data

Technologies:

Kafka, Kinesis, Pulsar, RabbitMQ Streams

💾 Event Sourcing

What it is:

"A pattern where instead of storing current state, you store all events that led to that state."

Characteristics:

  • Events are the source of truth
  • State is rebuilt by replaying events
  • Complete audit trail automatically
  • Focus on persistence and history

Examples:

  • Banking transactions
  • Order management systems
  • Version control (Git is event sourcing!)
  • Collaborative editing (Google Docs)

Technologies:

EventStore, Axon Framework, custom with Kafka/DB

💡 Concrete Examples
Understand the Difference

Event Streaming Example:

Real-time flow
// User clicks "Buy Now" button
User clicks → Event sent to Kafka → Multiple services react:
  - InventoryService: reduces stock
  - NotificationService: sends email
  - AnalyticsService: tracks conversion
  - RecommendationService: updates ML model

// Events flow through the system, consumed in real-time
// Not necessarily stored as the source of truth

Event Sourcing Example:

State reconstruction
// Bank account - DON'T store balance directly
// INSTEAD, store events:

Event 1: AccountOpened(accountId: "123", initialBalance: 0)
Event 2: MoneyDeposited(accountId: "123", amount: 100)
Event 3: MoneyWithdrawn(accountId: "123", amount: 30)
Event 4: MoneyDeposited(accountId: "123", amount: 50)

// Current balance = replay all events: 0 + 100 - 30 + 50 = 120
// You can rebuild ANY past state by replaying up to that point
// Complete audit trail built-in!
🔗 How They Work Together
Senior Insight

"Event Sourcing can use Event Streaming as the transport mechanism, but they're not the same thing."

Combined Architecture
// Event Sourcing: Store events as source of truth
public class OrderAggregate {
    private List<Event> events = new ArrayList<>();
    
    public void placeOrder(OrderPlacedEvent event) {
        events.add(event);  // Store in event store (Event Sourcing)
        publisher.publish(event);  // Also stream to Kafka (Event Streaming)
    }
}

// Event Streaming: Other services consume in real-time
@KafkaListener(topics = "orders")
public void handleOrderPlaced(OrderPlacedEvent event) {
    // React to event in real-time
    inventory.reserve(event.getItems());
}
🎯
Senior answer: "In modern systems, we often use Event Sourcing for critical aggregates that need full audit trails, and publish those events via Event Streaming (like Kafka) so other services can react in real-time. The events serve dual purpose: source of truth AND communication mechanism."
✅ When to Use Event Streaming
  • Real-time analytics and monitoring
  • Decoupling microservices
  • High-throughput data pipelines
  • Log aggregation
  • Notification systems
✅ When to Use Event Sourcing
  • Financial systems (audit requirements)
  • Domain models with complex workflows
  • Need for temporal queries ("state at time X")
  • Debugging production issues (replay events)
  • Compliance and regulatory needs
⚠️
Common mistakes: Don't say "they're the same thing" or "Event Sourcing is just using Kafka". Event Streaming is about transport, Event Sourcing is about persistence pattern.
🚨 Error Handling in Consumers
ℹ️
This is a critical production topic. Interviewers want to know you can build resilient systems that don't lose messages.
🎯 The Core Strategy
Must Know

Recommended Answer:

"Errors in a consumer are handled with retries, visibility timeout control, and fallback mechanisms like dead letter queues, ensuring messages aren't lost and are processed correctly."

Retry Logic — If processing fails, the message isn't deleted and can be retried (automatic or manual with exponential backoff).
Visibility Timeout — While a consumer processes a message, it's hidden from other consumers. If the consumer fails, the message returns to the queue.
Dead Letter Queue (DLQ) — If a message fails repeatedly, send it to a DLQ for analysis to avoid infinite loops.
Idempotency — The consumer must be idempotent to handle duplicate messages safely.
Observability — Log errors and metrics to identify failures and bottlenecks quickly.
♻️ Retry Strategies
Implementation
Java — Exponential Backoff Retry
public class MessageConsumer {
    private static final int MAX_RETRIES = 3;
    private static final long BASE_DELAY = 1000; // 1 second
    
    public void processMessage(Message message) {
        int attempt = 0;
        
        while (attempt < MAX_RETRIES) {
            try {
                // Process the message
                businessLogic.process(message);
                
                // Success - delete message
                sqs.deleteMessage(message);
                return;
                
            } catch (TransientException e) {
                // Temporary error - retry with backoff
                attempt++;
                long delay = BASE_DELAY * (long) Math.pow(2, attempt);
                Thread.sleep(delay);
                
            } catch (PermanentException e) {
                // Permanent error - send to DLQ immediately
                logger.error("Permanent error, sending to DLQ", e);
                dlq.send(message);
                sqs.deleteMessage(message);
                return;
            }
        }
        
        // Max retries exceeded - send to DLQ
        logger.warn("Max retries exceeded for message: {}", message);
        dlq.send(message);
        sqs.deleteMessage(message);
    }
}
🔄 Idempotency Pattern
Production Essential

"Processing the same message multiple times should not break the system or create duplicate effects."

Java — Idempotent Consumer
@Service
public class PaymentProcessor {
    @Autowired private PaymentRepository paymentRepo;
    
    public void processPayment(PaymentEvent event) {
        String idempotencyKey = event.getPaymentId();
        
        // Check if already processed (idempotency check)
        if (paymentRepo.existsByIdempotencyKey(idempotencyKey)) {
            logger.info("Payment already processed: {}", idempotencyKey);
            return; // Safe to ignore - already done
        }
        
        // Process payment
        Payment payment = new Payment();
        payment.setIdempotencyKey(idempotencyKey);
        payment.setAmount(event.getAmount());
        payment.setStatus("COMPLETED");
        
        // Save atomically
        paymentRepo.save(payment);
        
        logger.info("Payment processed successfully: {}", idempotencyKey);
    }
}
💡
Key insight: "Use a unique ID from the message (like requestId or transactionId) to track which messages have been processed. Store this in your database with the business entity."
⚡ Transient vs Permanent Errors

Transient (retry):

  • Network timeout
  • Database temporarily unavailable
  • Rate limit exceeded
  • Service temporarily overloaded

Permanent (DLQ immediately):

  • Invalid message format
  • Business rule violation
  • Authentication failure
  • Data not found (and won't exist)
🛡️ Circuit Breaker Pattern

For cascading failures, implement circuit breaker to prevent overwhelming downstream services.

// Using Resilience4j
@CircuitBreaker(name = "payment")
public void callPaymentAPI() {
    // If this fails repeatedly,
    // circuit opens and fails fast
}

🔥 Load Testing
📊 How Did You Do Load Testing?
Common Question

"In my projects, I perform load testing by simulating real traffic to validate system behavior under different load levels."

Define scenarios — Based on real usage: critical endpoints, concurrent user peaks, main business flows (login, frequent queries, heavy processes like payments).
Choose tools — Apache JMeter, Gatling, or k6 to generate concurrent load.
Execute progressive tests — Baseline (normal load), Stress testing (until system breaks), Spike testing (sudden peaks), Soak testing (sustained load over time).
Analyze key metrics — Latency (response time), Throughput (requests per second), Error rate, CPU and memory usage.
Optimize bottlenecks — Slow database queries, concurrency issues, lack of caching. Implement solutions like Redis caching, connection pool tuning, or query optimization.
Validate improvements — Repeat tests to confirm optimizations and ensure stability.
🛠️ Tools
  • JMeter: GUI-based, widely used
  • Gatling: Scala-based, great reports
  • k6: JavaScript, developer-friendly
  • Locust: Python-based
📊 Test Types
  • Baseline: Normal expected load
  • Stress: Push until failure
  • Spike: Sudden traffic bursts
  • Soak: Long duration test
📈 Key Metrics
  • Response time (p50, p95, p99)
  • Throughput (RPS)
  • Error rate (%)
  • Resource usage (CPU/Memory)
