🔗 Many-to-Many Relationships

Question asked

How do you create many-to-many relationships in Salesforce?

👆 Practice mode: click the blurred answer to reveal it
💡 Recommended Answer
Core Concept

"Salesforce has no native many-to-many field. You model it with a junction object that has two Master-Detail relationships, one to each parent. Every junction record links one record from each side, so a record on either side can relate to many on the other through many junction records."

Data model
Position__c  1 ───<  Job_Application__c  >─── 1  Candidate__c
 (master #1, primary)     (junction object)      (master #2, secondary)
🛠️ Steps
Create the junction object — e.g. Job_Application__c, named after the real-world thing that connects both sides.
Create the first Master-Detail field — to Position__c. This is the primary master: the junction inherits its Owner/Division behaviour from it.
Create the second Master-Detail field — to Candidate__c (the secondary master).
Expose it — add the related list to both parent page layouts; optionally add roll-up summary fields on either parent.
✅ Why Master-Detail on both sides
  • Roll-up summary fields on both parents
  • Deleting either parent cascades to the junction records
  • Junction inherits sharing from its masters (no Owner field)
  • An object can have at most 2 Master-Detail relationships
⚖️ When to use Lookups instead
  • Records must live independently of each other
  • Relationship is optional (Master-Detail is required)
  • Trade-off: no native roll-up summaries, no cascade delete

Standard examples: CampaignMember, OpportunityContactRole.

SOQL through the junction
-- Child → parent: who applied to what?
SELECT Id, Position__r.Name, Candidate__r.Name
FROM   Job_Application__c

-- Parent → child: a position with all its candidates
SELECT Name, (SELECT Candidate__r.Name FROM Job_Applications__r)
FROM   Position__c

🧬 Object Relationship Types

Question asked

Can you describe the types of connections (relationships) between objects in Salesforce?

👆 Practice mode: click the blurred answer to reveal it
💡 Recommended Answer
Data modeling

"Objects are connected through relationship fields. The main types are Lookup (a loose link), Master-Detail (a tight link where the parent controls the child), Many-to-Many through a junction object, Self relationships, the Hierarchical relationship (User only), and External / Indirect lookups for external objects. Standard objects also use polymorphic lookups such as Owner or WhatId, which can point to several object types."

TypeLink strengthParent required?Ownership & sharingWhen the parent is deletedRoll-up summary
LookupLooseNo (can be made required)Child keeps its own owner and sharingField is cleared, or the deletion is blocked (your choice)Not natively (use Flow / Apex)
Master-DetailTightYes, alwaysChild inherits owner, sharing and security from the parentChildren are deleted (cascade)Yes, on the master
Many-to-ManyVia a junction objectBoth parentsInherited from the two mastersCascade from either parentYes, on both masters
🔁 Self relationship

A lookup from an object to itself, e.g. Account.ParentId builds an account hierarchy.

👔 Hierarchical

A special lookup available only on the User object, e.g. the user's Manager.

🌍 External lookup

A child (standard/custom) object pointing to an external object; matches on the external object's External ID.

↩️ Indirect lookup

An external child object pointing to a standard/custom parent, matched on a unique External ID field on the parent.

🔀 Polymorphic relationships

Fields like Task.WhatId, Task.WhoId and Owner can point to more than one object type. In SOQL use TYPEOF to read different fields per type:

TYPEOF
SELECT Id, Subject,
  TYPEOF What
    WHEN Account     THEN Name, Phone
    WHEN Opportunity THEN Name, Amount
  END
FROM Task
✅ Choose Master-Detail when…
  • The child makes no sense without the parent
  • You need roll-up summary fields
  • Sharing and ownership should follow the parent
✅ Choose Lookup when…
  • The child can exist on its own or the link is optional
  • The child needs a different owner or sharing
  • You want to avoid cascade deletes
💡
Conversion rules: Lookup → Master-Detail only works if every child record already has a parent. Master-Detail → Lookup only works if the parent has no roll-up summary fields on it.

⚙️ Custom Settings vs Custom Metadata

Question asked

What is the difference between custom settings and custom metadata types?

👆 Practice mode: click the blurred answer to reveal it
💡 Recommended Answer
Key idea: data vs metadata

"Both store configuration that code can read without queries on regular objects. The key difference: custom metadata records are metadata, so they deploy and package together with the code across environments. Custom settings records are data: only the definition deploys, the values must be loaded per org — but they support hierarchical values per org, profile or user."

Rule of thumb: "If the value must be deployed with the code and be the same logic in every org, I use custom metadata. If it must differ per user or profile, or be flipped at runtime by an admin or a data load, I use a hierarchical custom setting."

⚡ Trigger Best Practices

Question asked

Describe best practices to work with triggers.

👆 Practice mode: click the blurred answer to reveal it
🧱 1. Logic-less triggers

The trigger only routes events to a handler class. Business logic lives in classes you can test and reuse.

📦 2. Bulkify everything

A trigger receives up to 200 records per chunk. Work with collections (Set, Map, List), never one record at a time.

🚫 3. No SOQL or DML in loops

Query once before the loop (WHERE Id IN :ids) and do one DML after it. This is the #1 cause of governor-limit failures.

🎯 4. Pick the right context

Before: change the same record's fields (no extra DML). After: need the record Id or must touch related records.

♻️ 5. Prevent recursion

Guard re-entry with a static Set<Id> of processed records, or only act when a field actually changed (compare Trigger.oldMap).

🔑 6. No hard-coded Ids

Use Custom Metadata, Custom Labels or describe calls (e.g. record type by developer name).

⏱️ 7. Async for slow work

Callouts and heavy processing go to Queueable/Future/Platform Events — never inline in the trigger.

🔌 8. Bypass switch

A Custom Metadata or Custom Permission flag lets admins skip triggers during data loads and migrations.

🧪 9. Test in bulk

Test with 200+ records, positive and negative cases, with real assertions — not just coverage.

🔒 10. Be explicit about security

Declare with sharing / without sharing on handlers and enforce FLS where user data is exposed.

❌ SOQL + DML inside the loop
trigger ContactTrigger on Contact (after insert) {
  for (Contact c : Trigger.new) {
    Account a = [SELECT Id FROM Account
                 WHERE Id = :c.AccountId];
    a.Description = 'Has new contact';
    update a;
  }
}
// 200 records = 200 queries + 200 DMLs → LIMIT EXCEPTION
✅ Bulkified
Set<Id> accIds = new Set<Id>();
for (Contact c : (List<Contact>) Trigger.new) {
  if (c.AccountId != null) accIds.add(c.AccountId);
}
Map<Id, Account> accs = new Map<Id, Account>(
  [SELECT Id FROM Account WHERE Id IN :accIds]);
for (Account a : accs.values()) {
  a.Description = 'Has new contact';
}
update accs.values();  // 1 query + 1 DML

Senior answer: "One logic-less trigger per object that delegates to a handler; everything bulkified with no SOQL or DML in loops; before-context for same-record changes and after-context for related records; recursion guards; async processing for callouts; a bypass switch for data loads; and bulk tests with real assertions."

🧩 One Trigger per Object & Trigger Handlers

Questions asked
  • Why do we need one trigger per object?
  • Talk about trigger handlers.
👆 Practice mode: click the blurred answer to reveal it
💡 Why one trigger per object?
Key Reason

"Salesforce does not guarantee the execution order of multiple triggers on the same object and event. If two triggers both update a field, the final value can change unpredictably. A single trigger gives one entry point where I control the order of operations, recursion, bypass switches and testing."

  • Deterministic execution order (you decide it in the handler)
  • One place to add recursion control and bypass logic
  • Easier to read, debug and test
  • Fewer merge conflicts and deployment surprises
🧱 The Trigger Handler pattern
Architecture

The trigger is a thin router. A handler class holds the logic, split by context. A shared base class dispatches on Trigger.operationType.

AccountTrigger.trigger
trigger AccountTrigger on Account (
  before insert, before update, before delete,
  after insert, after update, after delete, after undelete) {
  new AccountTriggerHandler().run();
}
TriggerHandler.cls (base class)
public virtual class TriggerHandler {
  public void run() {
    switch on Trigger.operationType {
      when BEFORE_INSERT  { beforeInsert(); }
      when BEFORE_UPDATE  { beforeUpdate(); }
      when BEFORE_DELETE  { beforeDelete(); }
      when AFTER_INSERT   { afterInsert(); }
      when AFTER_UPDATE   { afterUpdate(); }
      when AFTER_DELETE   { afterDelete(); }
      when AFTER_UNDELETE { afterUndelete(); }
    }
  }
  protected virtual void beforeInsert()  {}
  protected virtual void beforeUpdate()  {}
  protected virtual void beforeDelete()  {}
  protected virtual void afterInsert()   {}
  protected virtual void afterUpdate()   {}
  protected virtual void afterDelete()   {}
  protected virtual void afterUndelete() {}
}
AccountTriggerHandler.cls
public with sharing class AccountTriggerHandler extends TriggerHandler {

  protected override void beforeInsert() {
    for (Account acc : (List<Account>) Trigger.new) {
      if (String.isBlank(acc.Rating)) acc.Rating = 'Cold';  // no DML needed in "before"
    }
  }

  protected override void afterUpdate() {
    Map<Id, Account> oldMap = (Map<Id, Account>) Trigger.oldMap;
    List<Account> changed = new List<Account>();
    for (Account acc : (List<Account>) Trigger.new) {
      if (acc.Industry != oldMap.get(acc.Id).Industry) changed.add(acc);  // only react to real changes
    }
    if (!changed.isEmpty()) AccountService.syncIndustry(changed);
  }
}
♻️ Simple recursion guard
public class TriggerGuard {
  private static Set<Id> processed = new Set<Id>();
  public static Boolean firstTime(Id recordId) {
    return processed.add(recordId); // false if already there
  }
}
🧭 Going further
  • Move logic into service classes; keep queries in selector classes (fflib-style)
  • Bypass via Custom Metadata (Trigger_Setting__mdt)
  • Mixed automation (Flows + triggers) shares one order of execution — document it

🛠️ Trigger Frameworks & Disabling Triggers

Questions asked
  • Tell me about trigger frameworks in Salesforce.
  • You are doing a data load in production and some triggers must be disabled during it. How would you do it?
👆 Practice mode: click the blurred answer to reveal it
💡 What is a trigger framework?
Core Concept

"A trigger framework standardizes how triggers are structured: one trigger per object that delegates to a handler, automatic dispatch by context, recursion control, a bypass mechanism and a predictable order of execution. It keeps every developer writing triggers the same way and makes them testable."

OptionScopeNeeds a deployment?Notes
Custom Permission assigned through a permission set to the load userOnly that userNoChecked with FeatureManagement.checkPermission(). Safest and auditable: nobody else is affected. Recommended.
Hierarchical Custom SettingPer user, profile or whole orgNo (it is data)Flip a checkbox for the load user. Easy to forget to switch it back.

Bypass check in the base class
public virtual class TriggerHandler {

  public void run() {
    if (isBypassed()) return;           // skip everything for the data-load user
    switch on Trigger.operationType { /* … same dispatch as before … */ }
  }

  private Boolean isBypassed() {
    if (FeatureManagement.checkPermission('Bypass_Triggers')) return true;  // custom permission
    Trigger_Settings__c s = Trigger_Settings__c.getInstance();                  // hierarchical setting
    return s != null && s.Disable_All_Triggers__c == true;
  }
}
🪜 Safe procedure
Plan it — decide which triggers, validation rules and flows must be skipped, and how the skipped logic will be reproduced afterwards (e.g. a batch job).
Scope the bypass to the load user — assign the permission set with the Custom Permission; avoid global switches.
Run the load — Bulk API or Data Loader, sensible batch size, after a test run in a sandbox.
Remove the bypass immediately — unassign the permission set / reset the setting.
Reconcile — compare counts and key values, then run any follow-up logic and keep an audit trail.
💡
Don't forget the rest of the automation: use the same Custom Permission in validation rules (NOT($Permission.Bypass_Triggers)) and in Flow entry conditions, so the load isn't blocked by them. Inside a single Apex transaction, frameworks also offer a static bypass('HandlerName') call.

🌐 Running an API Request from a Trigger

Question asked

How would you run an API request from a trigger?

👆 Practice mode: click the blurred answer to reveal it
🚨
Trap: you cannot make a synchronous callout from a trigger. Salesforce throws CalloutException: Callout from triggers are currently not supported. The callout must happen asynchronously.
💡 Recommended Answer
Core Concept

"The trigger runs inside a DML transaction, so it can't wait on an external system. I collect the record Ids in the handler and enqueue a Queueable job that implements Database.AllowsCallouts. The callout uses a Named Credential so no URL or secret is in code. For decoupled or multi-subscriber scenarios I publish a Platform Event instead."

  • Keeps the user's save fast and the transaction safe
  • An external timeout or failure never blocks or rolls back the DML
  • Failures can be logged, retried or chained
Handler → Queueable → Named Credential
// Inside the handler (after update)
protected override void afterUpdate() {
  Map<Id, Opportunity> oldMap = (Map<Id, Opportunity>) Trigger.oldMap;
  Set<Id> wonIds = new Set<Id>();
  for (Opportunity o : (List<Opportunity>) Trigger.new) {
    if (o.StageName == 'Closed Won' && oldMap.get(o.Id).StageName != 'Closed Won') {
      wonIds.add(o.Id);
    }
  }
  if (!wonIds.isEmpty()) System.enqueueJob(new SyncOpportunityJob(wonIds));
}

public class SyncOpportunityJob implements Queueable, Database.AllowsCallouts {
  private Set<Id> oppIds;
  public SyncOpportunityJob(Set<Id> ids) { this.oppIds = ids; }

  public void execute(QueueableContext ctx) {
    List<Opportunity> opps = [SELECT Id, Name, Amount FROM Opportunity WHERE Id IN :oppIds];

    HttpRequest req = new HttpRequest();
    req.setEndpoint('callout:ERP_API/opportunities');  // Named Credential: URL + auth
    req.setMethod('POST');
    req.setHeader('Content-Type', 'application/json');
    req.setBody(JSON.serialize(opps));

    HttpResponse res = new Http().send(req);
    if (res.getStatusCode() >= 300) {
      // log the failure / retry / notify
    }
  }
}

✅ Validation Rules

Question asked

Validation rules in Salesforce — how do they work?

👆 Practice mode: click the blurred answer to reveal it
💡 Recommended Answer
Core Concept

"A validation rule is a formula that returns TRUE when the data is invalid. If it evaluates to TRUE on save, the record is not saved and the configured error message is shown — at the top of the page or next to a field. They run on insert and update (not delete), no matter where the save comes from: UI, API, Apex, Flow or data import."

📐 Error Condition Formula

Returns TRUE for bad data. Use ISBLANK, ISPICKVAL, ISCHANGED, PRIORVALUE, ISNEW.

💬 Error Message

Clear and actionable: tell the user how to fix it, not just what is wrong.

📍 Error Location

Top of page, or attached to one specific field for better UX.

⏱️ Where it sits in the order of execution
System validation (required fields, formats, lengths)
Before-save flows, then before triggers
Custom validation rules run — values changed by before-triggers are validated too
Duplicate rules → record saved (not committed) → after triggers
Assignment/workflow rules, after-save flows … → commit
Formula examples
// 1. A Closed Won opportunity must have an amount
AND(
  ISPICKVAL(StageName, "Closed Won"),
  OR(ISBLANK(Amount), Amount <= 0)
)

// 2. Same rule with a bypass for admins / data loads (Custom Permission)
AND(
  NOT($Permission.Bypass_Validation),
  ISPICKVAL(StageName, "Closed Won"),
  OR(ISBLANK(Amount), Amount <= 0)
)

// 3. Contract number can't be edited once it has a value
AND(
  NOT(ISNEW()),
  ISCHANGED(Contract_Number__c),
  NOT(ISBLANK(PRIORVALUE(Contract_Number__c)))
)
✅ Best practices
  • Always provide a bypass (Custom Permission / Custom Setting)
  • Guard against nulls with ISBLANK
  • Keep formulas short; document the intent in the Description
  • Remember they also fire on integrations and imports
⚖️ Validation rule vs Apex addError()

Use a declarative rule for field-level conditions an admin can maintain. Use record.addError('message') in a trigger when the check needs queries, other records or complex logic.

💾 insert vs Database.insert

Question asked

What is the difference between Database.insert and a simple insert?

👆 Practice mode: click the blurred answer to reveal it
💡 Recommended Answer
Core Concept

"The insert statement is all-or-nothing: if any record fails it throws a DmlException and the whole statement is rolled back. Database.insert(records, allOrNone) lets me set allOrNone = false for partial success: good records are saved and I get a SaveResult per record describing the failures."

insert records;Database.insert(records, false)
On failureThrows DmlException; whole statement rolled backNo exception for record errors; valid records are saved
ResultNothing returned (Ids populated on the records)Database.SaveResult[] — one per record
Error handlingtry / catchisSuccess(), getErrors()
Extras—DmlOptions (assignment rules, duplicate rules), AccessLevel.USER_MODE
Use whenAny failure must abort the operationBulk loads / integrations where good records should still go through
Side by side
List<Account> accs = new List<Account>{
  new Account(Name = 'Valid Inc.'),
  new Account()                    // Name is required → this one fails
};

// 1) Simple DML: nothing is saved, exception is thrown
try { insert accs; }
catch (DmlException e) { System.debug(e.getMessage()); }

// 2) Partial success: 'Valid Inc.' is saved, failure is reported
Database.SaveResult[] results = Database.insert(accs, false);
for (Integer i = 0; i < results.size(); i++) {
  if (results[i].isSuccess()) {
    System.debug('Saved: ' + results[i].getId());
  } else for (Database.Error err : results[i].getErrors()) {
    System.debug(err.getStatusCode() + ': ' + err.getMessage() + ' | ' + err.getFields());
  }
}
💡
Detail that impresses: both forms count as one DML statement against the governor limit, and the default value of allOrNone is true. The same pattern applies to update, upsert, delete and undelete.

⏳ Batch vs Queueable Apex

Question asked

What is the difference between Batch and Queueable Apex?

👆 Practice mode: click the blurred answer to reveal it
💡 Recommended Answer
Async Apex

"Batch Apex is built for large data volumes: it splits records into chunks, runs each chunk in its own transaction with fresh governor limits, and can process up to 50 million records. Queueable Apex is a lightweight, flexible async job: it accepts complex parameters, can be chained, and is the natural choice for work started from a trigger or a service — but it processes everything in one transaction."

🔁 Custom Retry Mechanism for a Batch

Question asked

You have a batch and you need a custom retry mechanism. How would you build it?

👆 Practice mode: click the blurred answer to reveal it
💡 Recommended Answer
Resilience

"Batch Apex has no built-in retry, so I build it around three ideas: capture the records that failed (per record, with Database.Stateful or a log object), classify the error as transient or permanent, and in finish() re-launch a batch only for the failed Ids with an attempt counter, exponential back-off and a maximum number of attempts. For failures I can't catch — like limit exceptions — I use BatchApexErrorEvent."

Retry with back-off
public class SyncAccountsBatch implements Database.Batchable<SObject>, Database.Stateful,
                                          Database.AllowsCallouts, Database.RaisesPlatformEvents {
  private static final Integer MAX_ATTEMPTS = 3;
  private Set<Id> onlyIds;                          // null on the first run
  private Integer attempt;
  private Set<Id> failedIds = new Set<Id>();       // survives between chunks (Stateful)

  public SyncAccountsBatch() { this(null, 1); }
  public SyncAccountsBatch(Set<Id> ids, Integer attempt) { this.onlyIds = ids; this.attempt = attempt; }

  public Database.QueryLocator start(Database.BatchableContext bc) {
    String soql = 'SELECT Id, Name FROM Account WHERE Needs_Sync__c = true';
    if (onlyIds != null) soql += ' AND Id IN :onlyIds';      // retries only the failed Ids
    return Database.getQueryLocator(soql);
  }

  public void execute(Database.BatchableContext bc, List<Account> scope) {
    for (Account a : scope) {
      try {
        ErpClient.push(a);                                  // callout
      } catch (ErpClient.TransientException e) {         // timeouts, 5xx, row locks…
        failedIds.add(a.Id);
      } catch (Exception e) {
        // permanent error → log it, do NOT retry
      }
    }
  }

  public void finish(Database.BatchableContext bc) {
    if (failedIds.isEmpty()) return;
    if (attempt < MAX_ATTEMPTS) {
      Integer delayMinutes = 5 * (Integer) Math.pow(2, attempt - 1);   // 5, 10, 20 … (exponential back-off)
      System.scheduleBatch(new SyncAccountsBatch(failedIds, attempt + 1),
                           'SyncAccounts retry #' + (attempt + 1), delayMinutes, 50);
    } else {
      // out of attempts → store the Ids in a "Failed_Sync__c" object and alert the team
    }
  }
}
🛟 Catching what try/catch can't: BatchApexErrorEvent

A limit exception can't be caught inside execute(). If the batch implements Database.RaisesPlatformEvents, Salesforce publishes a BatchApexErrorEvent for the failed chunk, and a trigger can react to it:

Subscriber
trigger BatchErrorTrigger on BatchApexErrorEvent (after insert) {
  for (BatchApexErrorEvent e : Trigger.new) {
    // JobScope = comma-separated Ids of the chunk that failed (even on LIMIT exceptions)
    Set<Id> failed = new Set<Id>();
    for (String s : e.JobScope.split(',')) failed.add(Id.valueOf(s.trim()));
    // log e.ExceptionType / e.Message, then re-enqueue the failed Ids with attempt control
  }
}
✅ Design checklist
  • Make the processing idempotent (safe to run twice)
  • Cap the attempts and use exponential back-off
  • Retry only transient errors; send permanent ones to a log
  • Persist retry state (custom object) if it must survive for hours
  • Alert when attempts are exhausted
⚠️ Pitfalls
  • Retrying the whole batch instead of just the failed Ids
  • Infinite retry loops (no maximum)
  • Huge Database.Stateful collections blowing the heap
  • Running two retries of the same job at once

📡 Platform Events

Question asked

Tell me about platform events.

👆 Practice mode: click the blurred answer to reveal it
💡 Recommended Answer
Event-driven

"Platform events are Salesforce's publish/subscribe messaging mechanism for event-driven architecture. A publisher sends an event message to the event bus and any number of subscribers react to it asynchronously, fully decoupled from each other. They are defined like custom objects with the __e suffix."

📤 Publishers
  • Apex: EventBus.publish()
  • Flow (Create Records / publish action)
  • REST / SOAP / Pub/Sub API from external systems
📥 Subscribers
  • Apex trigger (after insert only)
  • Platform-event-triggered Flow
  • LWC / Aura via lightning/empApi
  • External clients: CometD / Pub/Sub API
Publish & subscribe
// Publish

⏳ Retention & replay

High-volume events stay in the event bus for 72 hours. Every message has a replay ID, so a subscriber can catch up on events it missed within that window.

🔀 Publish behavior

Publish After Commit (default): only published if the transaction commits. Publish Immediately: published right away and can't be rolled back.

🔁 Error handling

In an Apex subscriber, throw EventBus.RetryableException to retry, and use setResumeCheckpoint to control where processing resumes.

🛡️ Record vs Field Security

Questions asked
  • Describe the difference in security for records and for object fields.
  • How is security different in Salesforce?
👆 Practice mode: click the blurred answer to reveal it
💡 Recommended Answer
Layered model

"Salesforce security is layered. Object (CRUD) and field-level security (FLS) decide what kind of data a user can touch — they are granted through profiles and permission sets. Record-level security decides which rows the user sees — it comes from the sharing model. A user needs to pass every layer."

1 · Organization level

Login hours and IP ranges, MFA, password policies, session settings.

2 · Object level (CRUD)

Create / Read / Edit / Delete on an object — via profiles, permission sets and permission set groups.

3 · Field level (FLS)

Visible / Read-only / Editable per field, for each profile or permission set.

4 · Record level (sharing)

Org-Wide Defaults (the most restrictive baseline) → role hierarchy → sharing rules → manual sharing, teams, territories, Apex managed sharing. You open up access from a restrictive baseline.

🧠 Example

A user has Read on Account (object), cannot see Annual Revenue (FLS), and only sees accounts they own or that are shared with them (record level). Three independent checks.

🧠 Query Fields the User Can't Access

Scenario asked

You are building a query and realize the user won't have access to several of its fields — but you still need them for your calculations. How do you build the query so it can read them without changing the user's permissions?

👆 Practice mode: click the blurred answer to reveal it
💡 Recommended Answer
Scenario

"I run that query in system mode — Apex's default — and I do not add WITH USER_MODE or WITH SECURITY_ENFORCED to it, because those would throw an exception when a field is inaccessible. I make the choice explicit with WITH SYSTEM_MODE, keep the class with sharing for record-level security, perform the calculation on the server, and return only the result — never the hidden fields."

Read in system mode — omit user-mode enforcement for this query; WITH SYSTEM_MODE documents the intent.
Decide record visibility separately — with sharing unless the business case truly needs without sharing (and then isolate it).
Compute server-side, return a DTO or a value — don't hand the full SObject to the UI/API.
If you must return records — run Security.stripInaccessible(AccessType.READABLE, records) first.
Encapsulate and document — a small, named service class with a comment explaining why elevation is justified, covered by tests.
Elevated read, minimal exposure
public with sharing class MarginService {

  @AuraEnabled(cacheable=true)
  public static Decimal calculateMargin(Id oppId) {
    // Intentional SYSTEM_MODE: Cost__c is hidden from the user by FLS but is
    // required for the calculation. Only the computed margin leaves this method.
    Opportunity opp = [
      SELECT Id, Amount, Cost__c
      FROM   Opportunity
      WHERE  Id = :oppId
      WITH   SYSTEM_MODE
      LIMIT  1
    ];
    if (opp.Amount == null || opp.Amount == 0) return null;
    return (opp.Amount - opp.Cost__c) / opp.Amount;   // value only, no hidden fields
  }
}
❌ Wrong approaches
  • Giving users a broader permission set just for this
  • WITH USER_MODE / WITH SECURITY_ENFORCED → throws when a field is inaccessible
  • Returning the full SObject to an LWC → leaks the hidden fields
  • without sharing everywhere "to make it work"
✅ Good alternatives
  • A formula field (it evaluates in system context, so users see the result without access to the inputs)
  • A roll-up or aggregate stored on a visible field
  • A dedicated service class, tested and security-reviewed

Get a list of Accounts and their Contacts, only for those Accounts that have at least one Opportunity with an Amount greater than 250,000 that is Closed Won.

👆 Practice mode: click the blurred answer to reveal it
🧭 How to think about it (3 steps)
Output shape → parent with children "Accounts and their Contacts" = FROM Account plus a child subquery on the Contacts relationship.
The filter is on a different object "Accounts that have at least one Opportunity…" can't be written as a join. Use a semi-join: Id IN (SELECT AccountId FROM Opportunity WHERE …).
Validate edge cases thresholds (> vs >=), nulls, "closed won" definition, accounts without contacts.
Solution
SELECT Id, Name,
       (SELECT Id, FirstName, LastName, Email FROM Contacts)
FROM   Account
WHERE  Id IN (
         SELECT AccountId
         FROM   Opportunity
         WHERE  Amount > 250000
         AND    StageName = 'Closed Won'
       )
🔍 Why it works
  • The semi-join returns each qualifying account once — no duplicates and no DISTINCT needed
  • "At least one" is exactly what IN (subquery) expresses
  • Contacts is the child relationship name (plural); custom relationships end in __r
  • The subquery must return a single Id/reference field
⚠️ Common mistakes
  • Filtering with WHERE Opportunities.Amount … in the outer query (not valid)
  • Putting the Opportunity filter inside the Contacts subquery (filters contacts, not accounts)
  • Using HAVING COUNT(...) where no aggregate is needed
  • Forgetting that Id IN is a semi-join, not a join — you can't select Opportunity fields this way
✨ Points that make the answer senior
  • Mention IsWon = true as a more robust alternative to the literal 'Closed Won' stage name
  • If only accounts that also have contacts are wanted, add AND Id IN (SELECT AccountId FROM Contact)
  • If a flat list is preferred: SELECT Id, FirstName, Account.Name FROM Contact WHERE AccountId IN (SELECT AccountId FROM Opportunity WHERE …)
  • In Apex, iterate with for (Account a : accounts) { for (Contact c : a.Contacts) { … } }
  • Test it in the Developer Console Query Editor and watch selectivity on large data volumes

Core Concept

Release to production — validate in production ahead of the window, then run a Quick Deploy of the validated package (valid for 10 days) so the release itself is fast.

🌿 Pull, Fetch, Merge & Rebase

Question asked

What do git pull, fetch, merge and rebase do, and how are they different?

👆 Practice mode: click the blurred answer to reveal it
💡 Recommended Answer
Core Concept

"git fetch only downloads new commits, branches and tags from the remote into your remote-tracking branches (like origin/main) — it never touches your working directory or current branch. git pull is fetch + merge (or fetch + rebase with --rebase): it also integrates those changes into the branch you are on."

Mental model
remote (origin)
     │  git fetch              downloads only
     ▼
origin/main  (remote-tracking branch)
     │  git merge origin/main  integrates into your branch
     ▼
main  (your local branch)

git pull  =  git fetch  +  git merge   (or  git fetch + git rebase)
🔎 git fetch — safe look
git fetch origin
git log HEAD..origin/main --oneline   # what's new?
git diff origin/main                  # how does it differ?
git merge origin/main                 # integrate when ready
⬇️ git pull — update now
git pull                  # fetch + merge
git pull --rebase         # fetch + rebase (linear history)

Pulling with uncommitted work can create conflicts you didn't expect — fetch first when in doubt.

Careful change

"I never delete metadata by hand in each org. ⏪ Rolling Back a Failing Release

Scenario asked

Your code is already in production and you see that it is failing. How can you roll back the code?

👆 Practice mode: click the blurred answer to reveal it
🚨
Key fact: Salesforce has no "undo deployment" button. A rollback is a forward deployment of the previous known-good state — and it only covers metadata, not data.
💡 Recommended Answer
Incident response

"First I stop the damage with a kill switch — a feature flag, a custom permission, deactivating the flow or trigger logic — without waiting for a deployment. Then I roll back through the pipeline: revert the release commit in Git, or redeploy the previous release tag, validate it and deploy to production. Anything the bad release added needs a destructive change, and any data it corrupted needs a separate fix from a backup."

Triage — confirm the failure matches the release (debug logs, Apex exception emails, Setup Audit Trail, deployment history) and measure the blast radius.
Mitigate immediately — flip the feature flag / bypass, reactivate the previous Flow version, disable the scheduled job or validation rule.
Choose: roll back or fix forward — roll back if the cause is unclear or the fix is large; fix forward through a hotfix branch if the fix is tiny and safe.
Roll back via Git + pipeline — revert the merge commit, let the pipeline validate and deploy it (or redeploy the previous tag).
Remove what was added — new classes, fields or flows are deleted with destructive changes.
Repair data and follow up — restore or correct affected records, verify, communicate, and write a post-mortem.
Revert and redeploy
# revert the release merge on main; the pipeline validates and deploys it
git revert -m 1 <merge-commit-sha>
git push origin main

# components the bad release ADDED must be removed explicitly
sf project deploy start --manifest manifest/package.xml \
  --post-destructive-changes manifest/destructiveChangesPost.xml \
  --test-level RunLocalTests --target-org prod
✅ Prepare before the release
  • Tag every release in Git and keep the artifact
  • Retrieve a metadata snapshot of production before deploying
  • Ship risky features behind a feature flag (Custom Metadata / Custom Permission)
  • Write the rollback plan into the release checklist
  • Validate first, deploy in a low-traffic window, monitor right after
⚠️ What does not roll back by itself
  • Data changed by the faulty code
  • New components the release created
  • Manual changes made directly in production
  • Note: a failed deployment is all-or-nothing, so production is never left half-deployed
🎯
Senior answer: "I mitigate first with a feature flag, then revert the release commit in Git and redeploy through the pipeline. I remove new components with destructive changes, repair data from backups, and I make rollback easy up front with release tags, pre-deployment snapshots and feature flags."

🧱 Deploying a New Required Field Safely

Scenario asked

A new requirement needs a new required field. How would you deploy it without breaking, for example, existing integrations?

👆 Practice mode: click the blurred answer to reveal it
🔁
Also asked in this interview: "How do you remove classes or fields from production?" — that one is already answered in Removing Unused Classes & Fields, so it isn't repeated here.
💡 Recommended Answer
Expand → Migrate → Enforce

"I wouldn't ship it as required on day one. I use a phased approach: deploy the field optional with field access and layout, backfill the existing records, release the integration changes, and only then enforce the requirement — ideally with a bypassable validation rule or a default value, so callers that don't know about the field never fail. Before deploying I also fix the Apex tests and automations that create records, because a missing required field makes them fail and blocks the deployment."

Map everything that creates or updates the object — API integrations and middleware, Data Loader/ETL jobs, Flows, Apex classes and triggers, test data factories, web-to-lead / Experience Cloud forms, email-to-case, and managed packages (which you can't change).
Release 1 — expand — deploy the field not required, grant access through a permission set (including the integration user), add it to layouts, and set a sensible default value if one exists.
Backfill existing data — populate legacy records (Bulk API or a batch job) so they don't fail the next time someone edits them.
Release 2 — integrations — integration owners start sending the value; update the API contract, and regression-test with real payloads in a sandbox.
Fix tests and automation — update test factories and Flows to populate the field, then run a validate-only deployment with all local tests.
Release 3 — enforce — activate the validation rule (or make the field required), monitor errors, and keep the rollback trivial: deactivating the rule.

⚠️ What breaks if you skip the plan
  • Apex tests fail with REQUIRED_FIELD_MISSING → the production deployment is blocked
  • Integrations get errors on every insert or update
  • Legacy records fail when someone edits them without a value
  • The integration user has no field access, so it can't even send the value
  • Managed-package code that creates records can't be changed
✅ Good practices
  • Deploy the field and its access in one release, enforce in a later one
  • Tell integration owners early and version the API contract
  • Test in a Partial Copy / Full sandbox with real payloads
  • Use a Custom Permission as the on/off switch
  • Document the rollback: deactivate the rule, keep the field
💡
Detail that impresses: checking "Required" on an existing field doesn't change old records, but any later edit of a record that has no value will fail — that's why the backfill comes before enforcement.

🔄 How Subscriptions Work in Salesforce CPQ

Question asked

Can you tell me how subscriptions work in Salesforce CPQ?

👆 Practice mode: click the blurred answer to reveal it
💡 Recommended Answer
Quote → Contract → Amend / Renew

"A subscription product is sold on a quote with a subscription term and a recurring price. When the opportunity is won and Contracted is checked, CPQ creates a Contract and one Subscription record (SBQQ__Subscription__c) for each subscription line. Those records are the source of truth for what the customer owns. Mid-term changes are amendments, which add new subscription records to the same contract with a prorated price, and renewals are generated automatically before the term ends."

⚙️ What defines a subscription
SettingMeaning
Subscription TypeRenewable (renews at the end of the term) · Evergreen (continues until cancelled) · One-time (sold once, not renewed)
Subscription PricingFixed Price (price per term from the list price) · Percent Of Total (a percentage of other lines, e.g. support = 20% of licences)

Subscription Term Unit / Proration PrecisionPackage settings that decide whether proration is calculated by month, by day or month + day
➗ Proration

When a line's effective term differs from its default term, CPQ scales the price:

Formula
prorate multiplier = Effective Subscription Term ÷ Default Subscription Term
prorated price     = subscription price × multiplier

// Example: 3 extra seats at 1,200 per seat per year (default term 12),
// added with 8 months left on the contract:
// 3 × 1,200 × (8 ÷ 12) = 2,400
✏️ Amendments
  • Started from the contract (Amend): CPQ creates a new opportunity and quote with the existing subscriptions
  • You enter the desired quantity; CPQ works out the difference (you need 3 more) and prorates the remaining term
  • Contracting the amendment updates the same contract with new subscription records — it does not create a new contract
  • Reducing quantity (or setting it to 0) cancels or downgrades
🔁 Renewals
  • CPQ can generate the renewal opportunity (and quote) before the contract ends, containing the subscription items and quantities
  • Contracted amendments are reflected in the renewal opportunity automatically
  • Uplift % can raise the price on renewal
  • Renewal model: contract-based or asset-based
📈 Multi-Dimensional Quoting (MDQ)

For ramp deals (different price or quantity per year), a line is split into segments, so each period can carry its own quantity and price while still being one product line.

🧾 Billing

CPQ stores what was sold. Invoicing comes from Salesforce Billing or an external ERP/billing system fed by the order and subscription data.

🎯
Senior answer: "Subscriptions in CPQ are quote lines with a term and recurring price. Contracting turns them into subscription records on a contract, amendments add prorated records to that same contract, and renewals are generated before it ends. The proration is the effective term divided by the default term."

Salesforce CPQ is the SteelBrick managed package with the SBQQ namespace. The newer revenue platform has a different data model and implementation approach. Confirm the product and scope before proposing a solution.

Para entenderlo
SBQQ identifica el paquete clásico. Experiencia con documentos, billing o quote-to-cash no demuestra automáticamente experiencia implementando Revenue Cloud.

3. Which objects should I know?

Interview answer
Product2, Pricebook2 and PricebookEntry define products and list prices. SBQQ__Quote__c and SBQQ__QuoteLine__c represent CPQ quotes. Product Options and Features model bundles; Contract and SBQQ__Subscription__c support subscription lifecycles. Orders use Order and OrderItem.

Para entenderlo
Una Product Option es el registro que relaciona el bundle con un producto opcional; no es el producto en sí. Los grupos de líneas son opcionales.

4. What is the difference between CPQ and quote-to-cash?

Interview answer
CPQ covers configuration, pricing and quoting. Quote-to-cash extends through contracting, order fulfillment, invoicing, payment collection and reconciliation.

Para entenderlo
Es un proceso empresarial que puede cruzar Salesforce, middleware y ERP. No es el nombre de un solo paquete.

5. What is a bundle?

Interview answer
A bundle is a configurable product with related options. Features organize options; quantity limits and business rules help produce a valid configuration.

Para entenderlo
Ejemplo ficticio: paquete de seguridad con central, cámaras y sensores. Una feature puede agrupar cámaras y otra sensores.

Interview answer
Configuration Attributes capture choices during bundle configuration and can influence related field values or rules, depending on the setup.

Para entenderlo
Ejemplo: tipo de instalación o región. No asumas que escribir un atributo cambia el precio: necesita configuración que use ese valor.

Interview answer
Use an Option Constraint for a straightforward dependency or exclusion between options. Use Product Rules for broader conditional logic, validation, selection, alerts or filtering.

Para entenderlo
Ejemplo: accesorio A requiere equipo B; una condición que además depende del mercado puede necesitar una Product Rule.

8. What is a dynamic bundle?

Interview answer
A dynamic feature uses configured filters to find eligible products rather than relying only on a fixed list of predefined options.

Para entenderlo
No significa simplemente que un bundle cambia con reglas. Repasa Dynamic Features y Filter Rules por separado.

9. How do you test a bundle?

Interview answer
Test required and optional selections, quantity limits, dependencies, exclusions, market eligibility, pricing and reconfiguration. Include amendments and renewals where applicable.

Para entenderlo
Prueba una combinación válida, una inválida y un cambio sobre una cotización existente.

Product Rules y Price Rules

Reglas · English answers / explicación en español

10. Product Rule versus Price Rule?

Interview answer
Product Rules control valid product selection and configuration. Price Rules update field values through conditions and actions during configuration or calculation.

Para entenderlo
Una Price Rule puede actualizar cantidades o campos auxiliares: no se limita a cambiar un precio.

11. What are the four Product Rule types?

Interview answer
Validation blocks an invalid configuration; Alert warns; Selection automates option behavior; Filter controls eligible products in dynamic features.

Para entenderlo
Una Validation Product Rule no es lo mismo que una Validation Rule de Salesforce que se evalúa al guardar un registro.

12. What makes up a Price Rule?

Interview answer
A Price Rule defines scope, evaluation events and order. Price Conditions decide whether it applies; Price Actions set target values. Lookup Queries can obtain values from a configured lookup table.

Para entenderlo
Piensa: cuándo evaluar, qué comprobar y qué actualizar. No todas las reglas necesitan condiciones o lookup queries.

13. What is a Configuration Rule?

Interview answer
A Configuration Rule associates a Product Rule with a configurable bundle. Product Rules may also operate at quote scope, depending on their configuration.

Para entenderlo
No todas las Product Rules requieren una asociación a un bundle específico.

14. What is a Summary Variable?

Interview answer
A Summary Variable aggregates values from supported records using filters, so rules can evaluate totals or counts rather than only one line.

Para entenderlo
Ejemplo: contar cámaras elegibles para comprobar si corresponde una condición comercial.

15. How do you model market-specific pricing?

Interview answer
Clarify currency, catalog eligibility and commercial policy. Use suitable price books, product configuration and rule or lookup data; test each market and avoid duplicating logic unnecessarily.

Para entenderlo
Ejemplo ficticio: la misma familia de servicios está disponible en dos mercados con monedas y condiciones distintas.

Pricing y descuentos

Cálculos · English answers / explicación en español

16. Where does the list price come from?

Interview answer
For list-priced products, CPQ normally obtains list price from the applicable PricebookEntry. Other pricing methods and overrides must be considered before interpreting the final price.

Para entenderlo
Revisa primero producto, price book, moneda, cantidad, fechas y método de pricing.

17. What is the price waterfall?

Interview answer
The waterfall records pricing stages such as List, Special, Prorated, Regular, Customer, Partner and Net prices. Pricing methods and package settings can change how adjustments apply.

Para entenderlo
No memorices una fórmula universal. Diferencia precio unitario, precio prorrateado y total de línea.

18. Range discount versus Slab discount?

Interview answer
Range applies the selected tier to the qualifying quantity. Slab applies each tier to the units within that band.

Para entenderlo
Ejemplo ficticio: 15 unidades; 1–10 sin descuento y 11–20 con 10%. En Slab solo las últimas 5 reciben ese 10%; en Range la banda alcanzada aplica a las 15.

19. Contracted Price versus Block Price?

Interview answer
A Contracted Price defines account-specific negotiated pricing for a product. Block Pricing sets a price for a quantity band.

Para entenderlo
Contracted Price se asocia a la cuenta; no lo describas simplemente como un precio guardado en Contract.

20. How would you separate installation and recurring charges?

Interview answer
Model the commercial charge types explicitly, configure subscription behavior appropriately, and expose separate totals for one-time and recurring charges. Confirm billing frequency and integration mappings.

Para entenderlo
Un campo custom llamado Monthly no convierte un producto en suscripción ni demuestra que exista una factura mensual.

21. Why is cost plus markup different from margin?

Interview answer
Markup is calculated on cost; margin is measured against selling price. Confirm which business metric is required.

Para entenderlo
Costo 80 más 25% de markup = precio 100; el margen sobre la venta es 20%.

22. What are the Price Rule evaluation events?

Interview answer
On Initialization, Before Calculate, On Calculate and After Calculate provide different points in the calculator sequence. Evaluation Order controls rules within an event.

Para entenderlo
Subir el orden de una regla no corrige necesariamente una dependencia que necesita otra fase del cálculo.

Quote to Order y Quote to Cash

Ciclo comercial · English answers / explicación en español

28. What is quote-to-order?

Interview answer
Quote-to-order turns an accepted commercial quote into an order and order lines ready for downstream processing.

Para entenderlo
Order Generation es la creación técnica de órdenes. Order Fulfillment es la ejecución o entrega.

29. Does accepting a quote automatically create an order?

Interview answer
Not necessarily. Quote acceptance, approvals, ordering and activation are distinct events. The configured process decides when an order is created.

Para entenderlo
Confirma las precondiciones, el estado de cálculo y si el proceso usa generación estándar o una API externa.

30. What must be preserved when creating an order?

Interview answer
Product identity, quantities, agreed prices, discounts, currency, dates, charge types and references to the originating quote and lines.

Para entenderlo
Verifica totales y correspondencia de líneas. La orden no debe reinterpretar silenciosamente lo aceptado.

31. What is order fulfillment?

Interview answer
Fulfillment delivers or activates what was sold. It may involve shipping, installation, service appointments or external provisioning.

Para entenderlo
La orden comercial, una Work Order y una Service Appointment cumplen funciones diferentes.

32. Invoice, payment and revenue: are they the same?

Interview answer
An invoice requests payment. A payment records cash received and its allocation. Revenue recognition follows the applicable accounting policy and delivery obligations.

Para entenderlo
Ejemplo educativo: cobrar un año por adelantado no implica reconocer todo ese ingreso inmediatamente. La política contable la define Finanzas.

33. What is the difference between quote-to-cash and order-to-cash?

Interview answer
Order-to-cash starts from the order and covers delivery, billing and collection. Quote-to-cash includes the earlier configuration, pricing, quoting and agreement steps.

Para entenderlo
Lead-to-cash comienza aún antes, con la captación y gestión comercial del prospecto.

Contratos y renovaciones

Suscripciones · English answers / explicación en español

34. What is a CPQ subscription record?

Interview answer
A subscription record represents a contracted recurring product with quantity, pricing and lifecycle information. Subscription configuration is distinct from invoice generation.

Para entenderlo
Un producto de suscripción, su Quote Line y el registro Subscription son elementos distintos.

35. How are contracts created?

Interview answer
Supported contracting processes can start from opportunities or orders depending on the implementation. Contracting produces the relevant contract, subscription or asset records according to product and package settings.

Para entenderlo
No todos los productos generan Subscription: revisa si son recurrentes o activos y cómo está configurado el proceso.

36. Amendment versus renewal?

Interview answer
An amendment changes an existing contract during its term. A renewal prepares the next commercial period, with its own opportunity and quote when generated.

Para entenderlo
Agregar dos licencias a mitad del periodo es amendment; continuar el siguiente periodo es renewal.

37. Are renewals always automatic?

Interview answer
CPQ supports renewal generation, but timing and automation depend on settings, contract fields and the surrounding process.

Para entenderlo
Evita decir que CPQ siempre genera la renovación solo porque se aproxima una fecha.

38. What is proration?

Interview answer
Proration adjusts subscription pricing for the effective service period. Dates, default term, term units and package precision settings determine the multiplier.

Para entenderlo
Ejemplo simplificado por meses: precio anual 1200, 6 de 12 meses = 600 por unidad. Con días y otras precisiones el resultado puede variar.

39. What are evergreen and co-termination?

Interview answer
Evergreen subscriptions continue until cancelled rather than having a normal fixed-term renewal. Co-termination aligns subscription end dates.

Para entenderlo
No describas evergreen como una renovación anual automática.

40. What is MDQ?

Interview answer
Multi-Dimensional Quoting splits a product into time-based segments so quantity or pricing can vary by period.

Para entenderlo
Ejemplo ficticio: 10 licencias el primer año y 20 el segundo. Es distinto de agrupar líneas visualmente.

💡 Interview Tips

✅ Do
  • Answer in 3 layers: one-line definition → how it works → a real example
  • Name governor limits and best practices unprompted
  • In the SOQL chat, state your assumptions (field and relationship names) before typing
  • Think out loud — explain why you chose a semi-join or an aggregate
  • Mention modern platform direction: External Client Apps, USER_MODE, Flow-first, source-driven development
  • Use short real stories: "In a project we bulkified a trigger and cut the limit errors to zero"
❌ Avoid
  • Saying a callout can be made directly from a trigger
  • Mixing up connected apps (inbound) and named credentials (outbound)
  • Putting SOQL or DML inside loops in any example
  • Claiming Apex enforces field-level security by default — it doesn't
  • Describing a CI/CD setup you haven't actually used
  • Guessing numbers; say "I'd verify the exact limit in the docs" instead
🎯 Strong Closing Lines
Make an impact
  • "I design triggers to be bulk-safe, logic-less and easy to test, and I move slow work to async processing."
  • "I choose the security mechanism deliberately: sharing keyword for records, USER_MODE or stripInaccessible for CRUD and FLS."
  • "I keep integrations secret-free in code by using Named Credentials, and decouple them with platform events when it makes sense."
  • "I treat releases as reversible: validated deployments, feature flags and a rollback plan before every production deploy."
